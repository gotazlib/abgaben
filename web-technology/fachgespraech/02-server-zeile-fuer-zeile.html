Teil 02 der Vorbereitung aufs Fachgespräch (Übersicht und Lernplan: README). Hier wird jede Datei unter server/ Zeile für Zeile erklärt, in Blöcken von höchstens fünf Zeilen. Zu jedem Block gibt es:

  • den Code mit den echten Zeilennummern (vom Script aus der Datei gelesen, darum immer exakt),
  • Was macht das? – in einfachen Worten,
  • Warum so? – die Begründung, oft mit der Alternative, die wir nicht genommen haben,
  • Folie – wo das Thema in den Kursfolien vorkommt («03/10» = Foliensatz 03, Folie 10), oder der Hinweis «nicht in den Folien»,
  • eine Prüfungsfrage mit kurzer Antwort, so wie sie im Fachgespräch kommen kann.

So lernt ihr damit: Die Datei im Editor öffnen (VS Code: Ctrl+G springt zur Zeile), hier den Block lesen, dann die Zeilen laut in eigenen Worten erklären, ohne abzulesen. Die Prüfungsfrage zuerst selbst beantworten, erst dann die Antwort lesen. Kapitel 1 bis 5 geben den Überblick, Kapitel 6 ist der eigentliche Rundgang.

1. Der Server in 60 Sekunden

«Unser Server ist ein Node.js-Programm mit Express. Er hält alle Sessions in einem Array im Arbeitsspeicher und bietet dafür eine REST-API unter /api/sessions an. Der Client schickt HTTP-Requests mit JSON, der Server prüft sie, ändert das Array und antwortet mit einem Statuscode und JSON. Alle 5 Sekunden entfernt ein Timer Teilnehmer, die sich länger als 15 Sekunden nicht gemeldet haben. Im Produktivbetrieb liefert derselbe Server auch die gebaute React-App aus.»

Das ist die Schichten-Ansicht aus Folie 02/4: Presentation (Browser mit React), Web-Server und Application in einem (Express, «vielfach eine Einheit mit Web-Server»). Statt einer Datenbank gibt es ein Array (In-Memory).

Beim Entwickeln laufen zwei Programme: Vite (Port 5173) liefert den Client und leitet alles unter /api an Express (Port 3000) weiter (client/vite.config.ts:10-12). Im Produktivbetrieb (NODE_ENV=production) gibt es nur Express auf einem Port: Er liefert die API und die gebauten Dateien aus client/dist (Folie 02/6: «Gib mir Datei xyz»).

Für alle Pfade zusätzlich: kaputtes JSON → 400, unbekannte Route → 404, unerwarteter Fehler → 500, immer als { "error": "…" } (server/src/app.ts:29-43).

Welche Methode wofür? (Methoden aus Folie 02/10-11)

  • GET liest nur: Liste und Tisch-Zustand. Darf beliebig oft kommen (Polling).
  • POST erstellt etwas, dessen ID der Server vergibt (Session, Teilnehmer) → 201 Created. POST auch für Aktionen ohne festen Wert: aufdecken, neue Runde.
  • PUT setzt einen Wert vollständig: die eigene Stimme, das Deck. Zweimal gleich = gleicher Zustand (idempotent).
  • DELETE entfernt: Session, Teilnehmer → 204 No Content (Erfolg ohne Body).

Statuscodes (Folie 02/10 nennt den «Status Code» im Header, die einzelnen Codes kommen in den Folien nicht vor):

Code Name Wann bei uns
200 OK Erfolg mit Daten (Standard von res.json())
201 Created Session oder Teilnehmer erstellt
204 No Content gelöscht oder verlassen, kein Body
400 Bad Request Body ungültig: kein JSON, Name leer/zu lang, Karte nicht im Deck, unbekanntes Deck
404 Not Found Session unbekannt, Teilnehmer unbekannt (beim Abstimmen), Route unbekannt
409 Conflict abstimmen, obwohl schon aufgedeckt ist
500 Internal Server Error unerwarteter Fehler im Server (Programmierfehler)

Eselsbrücke: 2xx «hat geklappt», 4xx «du (Client) hast etwas falsch gemacht», 5xx «ich (Server) habe etwas falsch gemacht».

4. Ablauf eines Requests von Anfang bis Ende

Am Beispiel «Anna wählt die Karte 5» (PUT /api/sessions/abc123/participants/p-1/vote). So erzählt ihr den Weg im Fachgespräch, mit dem Code daneben:

  1. Client: api/sessions.ts ruft fetch('/api/sessions/abc123/participants/p-1/vote', …) mit Methode PUT, Header Content-Type: application/json und dem Body {"value":"5"} auf (client/src/api/sessions.ts:155-171). Der Client-Teil ist in Teil 01 erklärt.
  2. Vite-Proxy (nur beim Entwickeln): Die Adresse beginnt mit /api, also schickt Vite den Request unverändert an http://localhost:3000 weiter (client/vite.config.ts:10-12).
  3. Node/Express nimmt an: app.listen hat Port 3000 geöffnet (server/src/index.ts:11-13). Express baut aus der Anfrage die Objekte req und res und schickt sie durch die Middleware, in der Reihenfolge von app.use in server/src/app.ts.
  4. express.json() liest den Body und legt { value: '5' } in req.body (server/src/app.ts:19). Wäre der Body kaputt, ginge es direkt zum Error-Handler (→ 400).
  5. Router: Der Pfad beginnt mit /api/sessions, also geht die Anfrage an den sessionsRouter (server/src/app.ts:21). Er vergleicht Methode und Rest-Pfad /abc123/participants/p-1/vote mit seinen Routen und findet PUT /:sessionId/participants/:participantId/vote. Express füllt req.params mit sessionId: 'abc123' und participantId: 'p-1'.
  6. Route-Handler (server/src/routes/sessions.ts:116-145), von oben nach unten: Session holen → sonst 404 · Person holen → sonst 404 · schon aufgedeckt → 409 · Body prüfen mit getVoteError (server/src/validation.ts:22-37) → sonst 400.
  7. Store ändern: castVote speichert die Stimme und deckt auf, wenn jetzt alle gewählt haben (server/src/store.ts:155-175).
  8. Antwort bauen: toSessionState(session, participant.id) macht die öffentliche Sicht: Annas Stimme ist drin, fremde Stimmen sind null (server/src/store.ts:39-62). res.json(…) wandelt sie in JSON-Text um, setzt Content-Type: application/json und Status 200.
  9. Zurück: Express schickt die Antwort, der Proxy reicht sie durch, fetch im Client bekommt sie, response.json() macht wieder ein Objekt daraus, PokerRoom setzt den State.
  10. Die anderen sehen die verdeckte Karte bei ihrem nächsten Poll (höchstens 1.5 s später).

Was passiert, wenn keine Route passt (z. B. GET /api/gibtsnicht)? Der Pfad beginnt nicht mit /api/sessions, also kommt der Router gar nicht dran. Im Produktivbetrieb sucht express.static noch eine Datei und findet keine. So landet die Anfrage bei der 404-Middleware am Ende (server/src/app.ts:29-31). Gleich geht es einem Pfad wie /api/sessions/abc123/gibtsnicht: Der Router bekommt ihn, findet aber keine passende Route und gibt ihn weiter. Was passiert bei einem Fehler im Code (z. B. Absturz in einer Route)? Express springt zum Error-Handler mit vier Parametern, der antwortet 500 und schreibt den Fehler ins Terminal (server/src/app.ts:34-43).

5. Sequenzdiagramme der sechs Abläufe

Die Diagramme zeigen, wer wem welche Nachricht schickt, von oben nach unten in der Zeit. Volle Pfeile sind Anfragen, gestrichelte Pfeile Antworten. Den Vite-Proxy lassen wir weg, er reicht beim Entwickeln nur durch.

5.1 Session erstellen

Anna klickt auf der Startseite «Neue Session erstellen» (client/src/components/HomePage.tsx:76-89).

Server: server/src/routes/sessions.ts:41-45 und server/src/store.ts:75-91. Wer die Session erstellt, ist danach nicht automatisch Teilnehmer: Die Tisch-Seite tritt ganz normal bei.

5.2 Session beitreten

Die PokerTablePage erscheint (nach «Erstellen» oder «Beitreten» in der Liste) und tritt in ihrem useEffect bei (client/src/components/PokerTablePage.tsx:30-71).

Server: server/src/routes/sessions.ts:84-101, server/src/validation.ts:10-19, server/src/store.ts:112-124. Ab jetzt pollt PokerRoom alle 1.5 s mit GET /api/sessions/abc123?participantId=p-1, und jeder Poll setzt lastSeen neu (Heartbeat, server/src/routes/sessions.ts:74-79).

5.3 Abstimmen

Anna klickt die Karte «5» (Weg im Client: client/src/components/PokerRoom.tsx:145-152).

Server: server/src/routes/sessions.ts:116-145, server/src/validation.ts:22-37, server/src/store.ts:155-175. Ein zweiter Klick auf dieselbe Karte schickt { "value": null } und zieht die Stimme zurück.

5.4 Aufdecken

Jemand klickt «Karten aufdecken», oder die letzte Stimme deckt automatisch auf (5.3).

Server: server/src/routes/sessions.ts:166-174, server/src/store.ts:177-179. Durchschnitt und Konsens rechnet der Client aus den Stimmen (client/src/utils/poker.ts), der Server schickt nur die Werte.

5.5 Neue Runde

Server: server/src/routes/sessions.ts:177-185, server/src/store.ts:181-186. Ein Deck-Wechsel (PUT …/deck) ruft am Ende dieselbe Funktion resetRound auf (server/src/store.ts:188-195).

5.6 Verlassen

Anna klickt «Verlassen». Der Button wechselt nur die Ansicht, den Request schickt das Cleanup (client/src/components/PokerTablePage.tsx:63-70).

Server: server/src/routes/sessions.ts:104-113, server/src/store.ts:126-135.

Und wenn jemand einfach den Tab schliesst? Dann kommt kein DELETE. Die Polls dieser Person bleiben aus, lastSeen wird alt, und der Timer aus server/src/index.ts:9 entfernt sie nach höchstens 20 Sekunden (15 s Timeout + bis zu 5 s bis zum nächsten Aufräumen, server/src/store.ts:142-152).
