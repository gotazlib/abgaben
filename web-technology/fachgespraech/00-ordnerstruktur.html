1. Das Wichtigste in drei Sätzen

  1. Im Projektordner liegen zwei eigene Projekte: client/ (React-App, gebaut mit Vite) und server/ (Express-API). Jedes hat ein eigenes package.json, «jedes package.json signalisiert ein Projekt» (Folie 03/10). Darum braucht es zum Entwickeln zwei Terminals.
  2. client/ ist die Projektvorlage des Dozenten (Folie 07/4), fast unverändert in der Konfiguration. Wir haben Code in src/ ergänzt, die Punkt-Dateien für Prettier und Git hinzugefügt und den Namen im package.json geändert.
  3. Beim Entwickeln öffnet der Browser http://localhost:5173 (Vite). Alle Anfragen an /api/… leitet Vite per Proxy an http://localhost:3000 weiter (Express). Der Browser spricht also nur mit einer Adresse, darum braucht es kein CORS.

5.9 oxlint – ohne eigene Konfiguration

Es gibt keine Datei .oxlintrc.json, weder in der Vorlage noch bei uns. pnpm lint startet oxlint mit seinen Standardregeln (Kategorie «correctness»: Code, der sicher falsch oder nutzlos ist, z. B. unbenutzte Variablen, debugger, doppelte Schlüssel). Standardmässig an sind die Plugins für JavaScript, TypeScript, «unicorn» und «oxc».

Achtung, ehrlich wissen: Das React-Plugin ist bei oxlint standardmässig aus (oxlint --help: «Enable react plugin, which is turned off by default»). Ohne Konfiguration prüft pnpm lint darum nicht, ob im useEffect eine Dependency fehlt oder ob in einer Liste der key fehlt. Wir haben das mit einer Testdatei ausprobiert: pnpm lint meldete nichts, pnpm exec oxlint --react-plugin meldete «React Hook useEffect has a missing dependency» und «Missing "key" prop». Unser echter Code läuft auch mit --react-plugin ohne eine Warnung durch. Im Editor zeigt die VS-Code-Erweiterung «Oxc» (README der Vorlage) die Hinweise je nach Einstellung.

Typische Prüfungsfrage: «Wie stellt ihr sicher, dass die Dependencies im useEffect stimmen?» Antwort: Wir haben jede Dependency-Liste von Hand begründet (Teil 01). Zusätzlich läuft oxlint --react-plugin ohne Warnung. Achtung: Das normale pnpm lint prüft Hook-Regeln nicht, weil das React-Plugin von oxlint ohne Konfiguration aus ist.

7. Was passiert bei pnpm install, dev, build, lint?

Alle Befehle laufen im Ordner client/ bzw. server/, nie im Projektordner (dort gibt es kein package.json). Wir haben jeden Befehl ausprobiert; die Ausgaben unten sind echt (gekürzt).

7.1 pnpm install

  1. pnpm liest packageManager und wechselt bei Bedarf selbst auf pnpm 12.11.2.
  2. pnpm liest package.json (welche Pakete?) und pnpm-lock.yaml (welche genauen Versionen?). Passt beides zusammen, wird nichts neu aufgelöst («Lockfile is up to date, resolution step is skipped»).
  3. Fehlende Pakete lädt pnpm aus der npm-Registry in einen zentralen Speicher auf dem Rechner («content-addressable store»). Jede Version liegt dort nur einmal, auch wenn zehn Projekte sie brauchen.
  4. In node_modules/.pnpm/ legt pnpm Hard-Links auf diese Dateien an (Folie 03/14: «Neuer Ansatz mit Hard-Links»), statt sie zu kopieren. Das ist schnell und spart Platz. Direkt in node_modules/ stehen nur Verknüpfungen (Symlinks) auf die Pakete aus package.json; deren eigene Abhängigkeiten liegen nur in node_modules/.pnpm/.
  5. Die Befehle der Werkzeuge (vite, tsc, oxlint, prettier) landen in node_modules/.bin/. Darum kann ein Script einfach vite schreiben.

7.2 pnpm dev

  • Client: pnpm führt das Script vite aus. Vite liest vite.config.ts, startet einen Server auf http://localhost:5173 und wartet. Requests auf /api leitet der Proxy an Port 3000 weiter.
  • Server: pnpm führt node --watch src/index.ts aus. Node entfernt die Typen, führt index.ts aus, das den Aufräum-Timer startet und mit app.listen(3000) auf Anfragen wartet. Ausgabe: «Scrum Poker API läuft auf http://localhost:3000». Bei jeder Änderung startet Node den Server neu; dabei gehen alle Sessions verloren (sie sind nur im Arbeitsspeicher).

Wichtig: Typfehler sieht man bei pnpm dev nur im Editor, nicht im Terminal. Darum vor dem Commit pnpm build laufen lassen.

8. Der Weg eines Requests: Browser → Vite-Proxy → Express

8.1 Beim Entwickeln (zwei Terminals)

Beispiel: Die Startseite lädt die Liste der Sessions (Polling in client/src/components/HomePage.tsx).

Schritt für Schritt (mit Dateien):

  1. client/src/components/HomePage.tsx ruft im useEffect die Funktion listSessions() auf.
  2. listSessions() in client/src/api/sessions.ts ruft send('GET', '/sessions') auf, und send ruft fetch('/api' + path, { method }) auf, also fetch('/api/sessions'): eine relative Adresse. Der Browser ergänzt sie zu http://localhost:5173/api/sessions.
  3. Der Vite-Dev-Server bekommt die Anfrage. Weil der Pfad mit /api beginnt, gibt er sie laut client/vite.config.ts:10-12 an http://localhost:3000/api/sessions weiter.
  4. Express (server/src/app.ts) liest bei Bedarf den JSON-Body (express.json()) und gibt alles unter /api/sessions an den Router in server/src/routes/sessions.ts weiter. Die Route GET / liest die Sessions aus server/src/store.ts und antwortet mit Status 200 und JSON.
  5. Vite reicht die Antwort unverändert an den Browser weiter.
  6. listSessions() prüft response.ok, liest response.json() und gibt die Liste zurück. HomePage speichert sie mit setSessions, React rendert die Liste neu.

Wenn Express nicht läuft: Vite kann nicht weiterleiten (im Vite-Terminal steht «http proxy error: /api/sessions … ECONNREFUSED») und antwortet dem Browser mit 502 Bad Gateway. createError() in client/src/api/sessions.ts macht daraus «Server nicht erreichbar.» (ausprobiert).

Warum kein CORS? Der Browser hat nur mit localhost:5173 gesprochen. Dass Vite intern mit Port 3000 redet, sieht er nicht. CORS (Cross-Origin Resource Sharing) wäre nur nötig, wenn der Browser selbst eine andere Adresse (anderer Port = anderer Ursprung) anfragen würde.

8.2 Wie man es im Browser sieht

DevTools (F12) → Tab Network (Folie 02/19–20): Die Anfrage heisst sessions, die Adresse ist http://localhost:5173/api/sessions, nicht Port 3000. Bei Klick darauf sieht man Methode, Statuscode, Header (Content-Type: application/json) und unter «Response» das JSON. Den Proxy selbst sieht der Browser nicht. Unter Application → Local Storage sieht man den gespeicherten Namen (scrum-poker:name).

8.3 Im Produktivbetrieb (ein Prozess, ohne Vite)

Nach pnpm build im Client startet man im Server NODE_ENV=production pnpm start. Dann gilt SERVE_CLIENT in server/src/config.ts, und server/src/app.ts liefert zusätzlich die fertigen Dateien aus client/dist aus (express.static). Browser und API haben wieder dieselbe Adresse (http://localhost:3000), also auch hier kein CORS. Vite läuft in diesem Fall gar nicht.

Typische Prüfungsfrage: «Zeigen Sie, wie ein Request vom Browser zum Server kommt.» Antwort: Komponente ruft eine Funktion aus api/sessions.ts auf, die ruft fetch('/api/…') auf. Der Browser schickt das an Vite auf Port 5173. Vite leitet alles unter /api per Proxy an Express auf Port 3000 weiter (vite.config.ts). Express gibt es an den Router, der den Store ändert und mit JSON antwortet. Die Antwort geht denselben Weg zurück; die Komponente setzt ihren State, React rendert neu.

Typische Prüfungsfrage: «Was ist der Unterschied zwischen Port 5173 und Port 3000?» Antwort: 5173 ist der Vite-Dev-Server, der den Client ausliefert. 3000 ist Express mit der API. Beim Entwickeln öffnet man nur 5173; Vite reicht /api an 3000 weiter.
