Teil A – Rundgang durch alle Dateien

A.0 Das Wichtigste in fünf Sätzen

  1. Der Server (Node.js mit Express) hält alle Sessions in einem Array im Arbeitsspeicher und bietet dafür eine REST-API unter /api/sessions an.
  2. Der Client (React) zeigt entweder die HomePage oder die PokerTablePage. Welche, entscheidet ein State in App: die aktive Session-ID (Ansichtswechsel mit State, 09/36).
  3. Der Client fragt den Server regelmässig nach dem aktuellen Stand (Polling mit window.setInterval im useEffect, 09/30) und zeigt ihn an. Jede Klick-Aktion ist ein Request, dessen Antwort sofort angezeigt wird.
  4. Der Name liegt in einem Context und wird mit dem Custom Hook useLocalStorage gespeichert (09/32). Nach einem Reload ist nur noch der Name da, man landet wieder auf der Home-Seite.
  5. Beitreten passiert im useEffect der PokerTablePage, Verlassen in dessen Cleanup. Verschwindet jemand ohne Verlassen (Tab zu, Reload), entfernt ihn der Server nach 15–20 s, weil seine Polls fehlen (Heartbeat).

B.1 «Zeigen Sie Komponente X. Welche Props hat sie, wer rendert sie?»

Vorgehen: Datei öffnen → Kommentar oben vorlesen (wozu, wer benutzt sie) → type Props zeigen → sagen, was jede Prop bedeutet → mit Ctrl+Shift+F nach <Komponentenname suchen und die Stelle zeigen, die sie rendert.

Beispiel CardDeck: «CardDeck zeigt die eigenen Karten. Sie bekommt vier Props: deck, welches Deck aktiv ist; selected, die eigene Stimme oder null; disabled, ob die Karten gesperrt sind; und onCardClick, eine Funktion, die sie beim Klick mit dem Kartenwert aufruft. Gerendert wird sie von PokerRoom (PokerRoom.tsx:220-225). Sie hat keinen eigenen State: Welche Karte gewählt ist, kommt vom Server über PokerRoom.»

Beispiel PokerTablePage: «Die PokerTablePage ist die Seite mit dem Tisch. Props: sessionId und onLeave. Gerendert wird sie von App, sobald dort eine Session-ID im State steht (App.tsx:17-20). Sie tritt beim Mount der Session bei und verlässt sie im Cleanup. Steht die participantId fest, rendert sie PokerRoom mit dem eigentlichen Tisch.»

Alle Komponenten haben weniger als acht Props (höchstens vier, z. B. SessionListItem), so wie in 08/48 empfohlen. Die Tabelle aller Komponenten steht in der Dokumentation, Kapitel 3.2.

B.2 «Warum liegt dieser State hier?»

Grundregel (Lifting State Up, 08/26–27): State liegt in der untersten Komponente, die ihn ändern muss, und gerade so weit oben, dass alle, die ihn lesen, darunter liegen.

State Ort Satz zum Merken
aktive Session-ID App Entscheidet, welche Seite zu sehen ist. Darum liegt er über beiden Seiten (09/36).
Name Context um die ganze App Home und Tisch brauchen ihn, gespeichert mit useLocalStorage.
Session-Zustand PokerRoom Alle Teile des Tisches brauchen ihn; PokerRoom ist der gemeinsame Elternteil.
participantId PokerTablePage Gehört zum Beitreten und Verlassen, das dort im useEffect passiert.
isDeleting SessionListItem Betrifft nur diesen einen Eintrag.
eigene Stimme kein eigener State Steht schon im Server-Zustand (me.vote). Doppelt gespeichert könnte sie veralten.
Ergebnis, Gültigkeit des Namens kein State Wird bei jedem Render berechnet (08/28: möglichst viel ableiten).

B.3 «Wie wechselt die App zwischen Home und Pokertisch?»

«Über State, so wie es der Leistungsnachweis seit der Änderung in 07/6 verlangt. In App.tsx, Zeile 11, liegt activeSessionId. Ist er null, zeigt App die HomePage, sonst die PokerTablePage mit der ID als Prop (Zeilen 17-20, Conditional Rendering). Die HomePage bekommt den Setter als Callback onJoin. Nach ‹Neue Session erstellen› ruft sie onJoin mit der neuen ID auf (HomePage.tsx:82, onJoin(sessionId)), beim Klick auf ‹Beitreten› ruft SessionListItem dasselbe mit der ID des Eintrags auf. Der Button ‹Verlassen› ruft onLeave auf, das setzt den State wieder auf null. Einen Router brauchen wir nicht, er ist nur noch eine optionale Erweiterung. Darum gibt es auch keinen Link auf eine Session, und nach einem Reload ist man wieder auf der Home-Seite.»

B.5 «Welche API-Routen gibt es, welche Methode, warum?»

«Alle unter /api/sessions in server/src/routes/sessions.ts. GET zum Lesen: die Liste und der Zustand eines Tisches. POST erstellt etwas Neues, dessen ID der Server vergibt: eine Session oder einen Teilnehmer, Antwort 201. PUT setzt einen Wert vollständig: die eigene Stimme und das Deck; zweimal derselbe Request ergibt dasselbe (idempotent). DELETE entfernt: Session oder Teilnehmer, Antwort 204 ohne Body. Aufdecken und Neue Runde sind Aktionen, darum POST. Fehler kommen immer als { error: '…' }: 400 bei ungültiger Eingabe, 404 wenn etwas nicht existiert, 409 wenn man nach dem Aufdecken noch abstimmen will.»

Die Methoden und Statuscodes kommen in den Folien Architektur und Technologien vor (02/10-13). Die ganze Tabelle steht in der Dokumentation, Kapitel 5.

B.6 «Was passiert, wenn der Server beim Polling nicht antwortet?»

«fetch wirft, weil keine Antwort kommt. send() in api/sessions.ts (Zeilen 35-37) macht daraus den Fehler ‹Server nicht erreichbar.›. Über den Vite-Proxy kommt stattdessen eine 502, die createError() in denselben Text übersetzt. Im Polling-Effekt von PokerRoom landet der Fehler im catch (PokerRoom.tsx:62-67): setPollError setzt die Meldung, session wird aber nicht gelöscht. Darum bleibt der Tisch mit dem letzten Stand sichtbar, darüber steht ‹… Neuer Versuch läuft …›. Das Intervall läuft weiter; sobald der Server wieder antwortet, setzt der nächste Poll pollError auf null. Startet der Server neu, sind die Daten weg, die nächste Antwort ist 404, also null, und wir zeigen ‹Diese Session existiert nicht (mehr)›. Die Home-Seite macht es genauso.»

B.7 «Warum ist dieser Type so definiert? Was ginge ohne ihn schief?»

  • DeckType = 'fibonacci' | 'tshirt': Mit string könnte man 'tshrit' schreiben, und es fiele erst zur Laufzeit auf. Die Union aus Literal Types lässt nur die zwei Werte zu (06/23).
  • vote: CardValue | null: null heisst «keine Stimme» bzw. «verdeckt». TypeScript zwingt jeden, der vote benutzt, an diesen Fall zu denken, z. B. participant.vote !== null in ParticipantSeat.tsx:20.
  • StoredParticipant vs. Participant: Der Server speichert die echte Stimme und lastSeen, der Client bekommt nur, was er sehen darf. Zwei Types machen sichtbar, dass hier etwas verborgen wird.
  • body: unknown in validation.ts: Von aussen kann alles kommen. Mit unknown erlaubt TypeScript keinen Zugriff, bevor wir mit typeof und in geprüft haben. Mit any würde TypeScript gar nichts prüfen. Die strenge Prüfung (strict, bei TypeScript 6 Standard) verbietet zudem ein stilles (implizites) any.
  • type statt interface: Beides beschreibt die Form eines Objekts. Die Folien empfehlen type (06/22), und 09/37 verlangt, es einheitlich zu machen. Darum steht überall type, auch bei den Props (type Props, wie in 08/15).

B.8 «Welches Problem löst Context? Wann sind Props besser?»

«Den Namen brauchen die HomePage (Eingabe) und die PokerTablePage (Beitreten). Ohne Context müsste App den Namen halten und an beide Seiten geben, wie in den Folien beim Lifting State Up (08/26). Das ginge bei uns auch, es sind nur zwei Ebenen. Die Aufgabenstellung verlangt für den Namen aber einen Context, darum legt main.tsx den UserProvider einmal um alles, und jede Komponente liest den Namen mit useContext(UserContext). Context ist nicht in den Folien, wir haben ihn aus der React-Dokumentation. Props sind besser für alles andere: Sie zeigen, woher die Daten kommen, und bei häufigen Änderungen wie dem Tisch-Zustand alle 1.5 s rendert nur der betroffene Teil neu. Context lohnt sich für wenige Werte, die selten wechseln und die viele Stellen brauchen.»

B.9 «Warum braucht es ein Cleanup im useEffect?»

«Ein Effekt startet etwas, das ausserhalb von React weiterläuft: ein Intervall oder eine Anmeldung am Server. Wird die Komponente entfernt (Unmount), muss das wieder aufhören (09/15). Bei uns gibt es drei Cleanups:

  1. Polling der Liste (HomePage.tsx:70-73): window.clearInterval, sonst liefen nach dem Wechsel zum Tisch weiter Requests für die Liste. Die Folien nennen das ein Memory Leak (09/30).
  2. Polling am Tisch (PokerRoom.tsx:76-79): window.clearInterval, sonst liefe das Polling nach dem Verlassen im Hintergrund weiter und schickte unnötige Requests (Memory Leak).
  3. Beitreten (PokerTablePage.tsx:63-70): Leave-Request, sonst sässe man nach dem Verlassen noch bis zum Timeout am Tisch.

Dazu kommt das ignore-Flag: Eine Antwort, die erst nach dem Cleanup ankommt, schreibt nicht mehr in den State.»

B.10 «Was macht StrictMode mit Effects?»

«StrictMode (main.tsx:17) startet in der Entwicklung jeden Effekt beim ersten Anzeigen zweimal: Effekt, Cleanup, Effekt (08/24, 09/3). So fällt sofort auf, wenn ein Cleanup fehlt. Beim Beitreten gehen dadurch zwei Join-Requests los. Das Cleanup des ersten Durchlaufs setzt dessen ignore auf true. Kommt seine Antwort, sieht der Code in PokerTablePage.tsx:40-47: ‹ich bin schon aufgeräumt›, und meldet den eben angelegten Teilnehmer sofort wieder ab. Übrig bleibt der Teilnehmer des zweiten Durchlaufs. Im gebauten Produktivcode läuft der Effekt nur einmal.»

B.11 «Was passiert bei einem Reload am Tisch?»

«Man landet wieder auf der Home-Seite, nur der Name ist noch da. So verlangt es der Leistungsnachweis seit 07/6. Die aktive Session-ID ist ein normaler State in App und nach dem Reload wieder null. Der Name kommt aus dem localStorage (useLocalStorage). Bei einem Reload läuft kein React-Cleanup, auf dem Server sitzt man also noch am Tisch. Weil von diesem alten Platz keine Polls mehr kommen, entfernt ihn der Server nach höchstens 20 Sekunden (Heartbeat-Timeout). Wer wieder mitmachen will, tritt über die Liste neu bei und bekommt eine neue participantId.»

B.12 «Kennt ihr Custom Hooks? Warum gibt es keinen Hook fürs Polling?»

«Ja, useLocalStorage in client/src/hooks/ ist ein Custom Hook, genau wie in der Übung aus Vorlesung 9 (09/32). Er kapselt useState und das Speichern im localStorage, und der UserProvider benutzt ihn. Fürs Polling haben wir bewusst keinen Hook gebaut. Es gibt zwei Stellen, und beide machen nach einer Antwort etwas anderes (die Liste behält bei Fehlern den alten Stand, der Tisch stoppt bei einer gelöschten Session das Intervall). Ein gemeinsamer Hook bräuchte dafür Parameter und Callbacks und wäre schwerer zu lesen als zwei kurze useEffect. So wie useAutoCounter in 09/30 sieht jedes Polling bei uns aus: window.setInterval im Effekt, window.clearInterval im Cleanup. Statt Requests abzubrechen (AbortController, nicht Kursstoff), ignorieren wir späte Antworten mit dem ignore-Flag.»

B.13 «Warum habt ihr keine Error Boundary und keine Tests mit einer Test-Library?»

«In den Projekt-Tipps steht ‹keine Class-Components› und ‹keine zusätzlichen Libraries ausser Express und optional React Router› (09/37). Eine Error Boundary gibt es in React nur als Klasse, darum haben wir sie weggelassen. Fehler von Server-Aufrufen fangen wir überall mit try/catch ab und zeigen eine Meldung. Ein Fehler beim Rendern wäre ein Programmierfehler; dagegen helfen strict in TypeScript, pnpm lint und das Ausprobieren. Test-Libraries wie Vitest wären zusätzliche Libraries und kommen in den Folien nicht vor. Wir prüfen mit pnpm lint, pnpm format:check und pnpm build (dabei läuft die Typprüfung) in beiden Ordnern und klicken jeden Ablauf in zwei Browserfenstern durch, auch auf Handy-Breite in den DevTools.»

B.14 «Warum zwei Projekte, und warum stehen manche Regeln doppelt?»

«Der Client ist die Projektvorlage aus dem Kurs (07/4), ein reines React-Projekt. Den Server haben wir als eigenes Node-Projekt daneben gelegt, wie in den Folien zu Node.js: ein package.json pro Projekt (03/10). Ein gemeinsamer Ordner für die Types bräuchte einen Workspace, den wir sonst nirgends erklären könnten. Darum stehen die Types der API und zwei Regeln zweimal da: die Karten pro Deck und die Namensprüfung (client/src/utils/poker.ts und server/src/rules.ts). Der Nachteil ist, dass man bei einer Änderung beide Stellen anpassen muss. Darauf weist der Kommentar oben in beiden Dateien hin. Vergisst man es, gibt es Fehler: Eine Karte, die nur der Client kennt, lehnt der Server mit 400 ab; eine Namensregel, die nur auf einer Seite geändert ist, führt zu anderen Meldungen als beim Server.»

B.15 «Wie läuft der Server mit TypeScript, ohne dass ihr ihn kompiliert?»

«Node.js 24 kann .ts-Dateien direkt ausführen. Es entfernt beim Laden einfach die Type-Angaben (Type Stripping) und führt den Rest als JavaScript aus. Darum steht in server/package.json nur node --watch src/index.ts. Das klappt, weil wir nur TypeScript benutzen, das man weglassen kann: Types, type-Imports, Type-Angaben an Variablen. Die Einstellung erasableSyntaxOnly in der tsconfig.json prüft genau das. pnpm build im Server macht nur die Typprüfung mit tsc, erzeugt aber keine Dateien. Im Client übersetzt Vite das TypeScript.»

Teil C – Fragenkatalog

# Frage Kurze Antwort
1 Was ist der Unterschied zwischen Props und State? Props kommen von aussen und sind in der Komponente nur lesbar (08/16). State gehört der Komponente, ändert sich mit der Setter-Funktion und löst ein neues Rendern aus.
2 Wie kommt die aktive Session-ID zur PokerTablePage? Sie liegt als State in App und geht per Prop sessionId nach unten. Gesetzt wird sie über den Callback onJoin, zurückgesetzt über onLeave.
3 Was heisst «Callback via Props»? Die Eltern-Komponente gibt eine Funktion als Prop nach unten, das Kind ruft sie auf, um etwas nach oben zu melden (State Flow, 08/25-27). Beispiel: onCardClick, onJoin, onDeleted.
4 Warum darf man State nicht direkt ändern? React merkt Änderungen nur über den Setter mit einem neuen Wert. Direkt verändert, rendert nichts neu. Darum filter() beim Löschen, das eine neue Liste erzeugt (08/33).
5 Wozu dient die key-Prop in Listen? Damit React beim Ändern der Liste weiss, welches Element welches ist (08/31). Wir nehmen stabile IDs (session.id, participant.id), nie den Index.
6 Was macht useEffect, und wann läuft er? Er führt Code nach dem Rendern aus, für alles ausserhalb von React (Server, Timer). Er läuft beim Mount und immer dann, wenn sich ein Wert im Dependency Array ändert. [] = nur beim Mount (09/13).
7 Warum ist der Callback im Effekt nicht direkt async? Ein Effekt darf nur eine Cleanup-Funktion zurückgeben, eine async-Funktion gibt aber ein Promise zurück (09/23). Darum eine innere async function und sie sofort aufrufen (09/24).
8 Was macht das ignore-Flag? Jeder Effekt-Durchlauf hat sein eigenes ignore. Das Cleanup setzt es auf true. Eine Antwort, die danach kommt, wird nicht mehr in den State geschrieben.
9 Warum ruft loadSession selbst window.clearInterval auf? Wurde die Session gelöscht, ist weiteres Abfragen sinnlos. Sonst ginge alle 1.5 s ein Request mit 404 raus.
10 Was heisst useState(() => …)? Die Funktion läuft nur beim ersten Render (Lazy Initial Value, 09/8). So wird localStorage nicht bei jedem Render gelesen.
11 Was heisst setSessions((current) => …)? Der Setter bekommt eine Funktion und ruft sie mit dem neusten State auf (09/7). Sicher, auch wenn sich der State inzwischen geändert hat (z. B. ein Poll ist angekommen).
12 Was ist ein Custom Hook? Eine Funktion, deren Name mit use beginnt und die selbst Hooks benutzt (09/26). Bei uns useLocalStorage.
13 Was bleibt nach einem Reload erhalten? Nur der Name (localStorage). Die aktive Session-ID ist normaler State und wieder null (07/6).
14 Wo seht ihr den gespeicherten Namen im Browser? DevTools → Application → Local Storage, Schlüssel scrum-poker:name (02/19-20).
15 Warum Polling und nicht WebSockets? Einfacher, passt zu REST, kommt in den Folien vor (09/30). Nachteil: bis 1.5 s Verzögerung und mehr Requests. Für ein Team von 5–10 Personen kein Problem.
16 Warum 1.5 s am Tisch und 3 s bei der Liste? Am Tisch soll es sich live anfühlen und der Heartbeat braucht Abstand zum 15-s-Timeout. Die Liste ist weniger dringend.
17 Was ist CORS und warum braucht ihr es nicht? Der Browser blockiert Antworten von einer anderen Adresse (auch ein anderer Port zählt), wenn der Server es nicht erlaubt. Der Vite-Proxy macht /api zur selben Adresse wie die Seite.
18 Was macht express.json()? Middleware, die JSON-Bodies liest und in req.body ablegt. Bei kaputtem JSON wirft sie einen SyntaxError → unser Error-Handler → 400.
19 Was ist Middleware? Eine Funktion (req, res, next), die vor oder nach den Routen läuft. Sie kann die Anfrage verändern, beantworten oder mit next() weitergeben.
20 Woran erkennt Express den Error-Handler? An den vier Parametern (err, req, res, next). Darum steht _next da, obwohl er nicht benutzt wird.
21 Warum ist app.ts von index.ts getrennt? app.ts beschreibt, was die App tut, index.ts startet sie und den Aufräum-Timer. So ist jede Datei kurz und hat eine Aufgabe.
22 Warum prüft der Server den Namen, obwohl der Client schon prüft? Jeder kann mit curl Requests schicken. Prüfung im Client = Komfort, Prüfung im Server = Sicherheit. Beide benutzen dieselbe Regel validateName.
23 Warum 201 beim Erstellen und 204 beim Löschen? 201 Created: etwas Neues ist entstanden. 204 No Content: Erfolg, aber es gibt nichts zurückzuschicken.
24 Wann kommt 409? Wenn jemand nach dem Aufdecken noch abstimmen will. Die Anfrage ist richtig gebaut, passt aber nicht zum aktuellen Zustand.
25 Wie verhindert ihr, dass man Stimmen in den DevTools sieht? Der Server schickt vor dem Aufdecken nur hasVoted, vote ist null (store.ts:46). Im Network-Tab sieht man das in der Antwort.
26 Warum sieht man die eigene Stimme vor dem Aufdecken? Damit der Client die gewählte Karte aus dem Server-Zustand hervorheben kann, ohne sie selbst zu speichern. Für die eigene Person ist sie kein Geheimnis.
27 Wann wird automatisch aufgedeckt? Wenn alle (mindestens eine Person) gewählt haben: nach einer Stimme oder wenn die letzte Person ohne Stimme geht.
28 Warum startet ein Deck-Wechsel eine neue Runde? Alte Karten (z. B. 13) gibt es im neuen Deck nicht, der Durchschnitt wäre sinnlos.
29 Wie zählen ? und ☕? Nicht zum Durchschnitt, aber zur Anzahl Stimmen. Nur ?/☕ → Durchschnitt «–».
30 Was heisst Konsens bei euch? Mindestens zwei Stimmen und alle gleich (auch zweimal ?).
31 Unterschied unknown und any? Beide nehmen alles an. Bei unknown verlangt TypeScript eine Prüfung vor der Nutzung, any schaltet die Prüfung ab. Beides kommt in den Folien nicht vor; wir benutzen unknown nur dort, wo Daten von aussen kommen.
32 Was macht const joinRequest: JoinSessionRequest = req.body? req.body hat bei Express den Type any. Erst nach der Prüfung in validation.ts geben wir ihm unseren Type, damit TypeScript ab dort joinRequest.name kennt.
33 Was bedeutet das ! in getElementById('root')!? «Dieser Wert ist sicher nicht null». Das <div id="root"> steht in index.html. So auch in 09/3.
34 type oder interface? Beides beschreibt Objekte. Wir nehmen überall type, wie in den Folien empfohlen (06/22), und einheitlich (09/37).
35 Was macht import type? Importiert nur einen Type, der beim Übersetzen ganz wegfällt. Mit verbatimModuleSyntax (aus der Vorlage) ist das Pflicht (07/12).
36 Was macht async/await? await wartet auf ein Promise, ohne den Browser zu blockieren. Fehler fängt man mit try/catch (09/17).
37 Warum wirft fetch bei 404 keinen Fehler? fetch wirft nur, wenn keine Antwort kam. Jede HTTP-Antwort ist für fetch ein Erfolg. Darum prüfen wir response.ok bzw. response.status selbst (09/23).
38 Warum gibt getSession bei 404 null zurück statt eines Fehlers? «Gibt es nicht» ist ein normaler Fall, kein Absturz. null lässt sich mit einem if prüfen, ohne try/catch.
39 Warum .catch(() => {}) beim Leave-Request? Ein Fehler beim Verlassen ist egal, der Heartbeat-Timeout entfernt die Person trotzdem. Ohne .catch gäbe es eine «Uncaught (in promise)»-Meldung in der Konsole.
40 Was ist ein kontrolliertes Eingabefeld? Der Wert des Felds kommt aus dem State (value), jede Eingabe geht über onChange zurück. React ist die einzige Quelle für den Inhalt. Bei uns das Namensfeld und das <select>.
41 Wie liest ihr den Wert aus einem <select>? Im Handler mit ChangeEvent<HTMLSelectElement> steht der gewählte Wert in event.target.value (08/42). Weil das ein string ist, suchen wir den passenden DeckType in DECK_TYPES.
42 Was macht children bei PokerTable? Alles, was zwischen <PokerTable> und </PokerTable> steht, kommt als Prop children an (08/17). PokerTable zeigt es in der Mitte, ohne zu wissen, was es ist.
43 Was ist Conditional Rendering, was Conditional Styling? Rendering: je nach Bedingung eine andere Komponente oder nichts (&&, Ternary, if mit return). Styling: je nach Bedingung eine andere CSS-Klasse (className={… ? … : …}), 08/36-37.
44 Warum hat jede Komponente eine eigene CSS-Datei? So steht in 08/19: Styles liegen neben der Komponente, die sie braucht. Das Präfix im Klassennamen verhindert, dass sich Komponenten gegenseitig stören.
45 Was macht box-sizing: border-box? width schliesst Padding und Rahmen ein (Box-Modell, 04/19-21). Elemente werden nicht unerwartet breiter. Bei uns der Mini-CSS-Reset oben in index.css.
46 Flexbox oder Grid – wann was? Flexbox für eine Richtung (Reihe von Buttons, Karten, Plätzen), Grid für Spalten und Zeilen (Home-Seite).
47 Was heisst Mobile First? Zuerst Regeln für kleine Bildschirme schreiben, mit min-width-Media-Queries für grössere ergänzen.
48 Wozu role="alert", role="status" und label mit htmlFor? Screenreader lesen Fehler sofort und Ladehinweise höflich vor; das Label gehört fest zu seinem Feld. Je ein Attribut, mehr Barrierefreiheit bauen wir nicht ein.
49 Was passiert, wenn zwei Personen gleichzeitig das Deck wechseln? Der Server bearbeitet Requests nacheinander. Der zweite gewinnt, beide sehen beim nächsten Poll denselben Zustand.
50 Was passiert mit den Daten bei einem Neustart des Servers? Alles weg (Array im Arbeitsspeicher). Bewusst so, es gibt keine Datenbank.
51 Warum verlasst ihr die Session nicht beim Schliessen des Tabs? Beim Schliessen kommt nicht sicher noch ein Request an (Absturz, Akku leer, Netz weg). Darum verlassen wir uns auf den Heartbeat: Ein geschlossener Tab ist nach höchstens 20 s weg.
52 Was passiert mit zwei Tabs derselben Person? Jeder Tab tritt selbst bei und bekommt eine eigene participantId: zwei Einträge am Tisch.
53 Wie startet man die App? Zwei Terminals: im Ordner server/ pnpm dev (Port 3000), im Ordner client/ pnpm dev (Port 5173). Vorher in beiden einmal pnpm install.
54 Was prüft pnpm lint? oxlint (aus der Vorlage) sucht typische Fehler, z. B. fehlende Werte im Dependency Array. 09/37 verlangt, es auszuführen.
55 Wozu Prettier? Formatiert den Code einheitlich (ohne Semikolons, einfache Anführungszeichen). pnpm format:check prüft, ob alles formatiert ist (09/37).
56 Was habt ihr an der Projektvorlage geändert? Scripts, vite.config.ts, index.html, tsconfig*.json und die Ordner components/, hooks/, types/ sind gleich. Geändert: index.css wird in main.tsx vor App importiert (Komponenten-CSS gewinnt), der UserProvider liegt um App, dazu die Ordner api/, context/, utils/ (09/37), und index.css/App.css enthalten unsere Styles.
57 Was passiert, wenn ein Tab lange im Hintergrund liegt? Chrome bremst nach etwa fünf Minuten die Timer auf einen Aufruf pro Minute. Dann fehlen die Polls, der Server entfernt die Person nach 15 s, und beim Zurückkommen steht «Du bist nicht mehr am Tisch». Neu beitreten über die Liste. Für eine Schätzrunde nehmen wir das in Kauf (Doku Kap. 8).
58 Warum gap in Flexbox? Die Folien zeigen Abstände zwischen Elementen nur bei Grid (column-gap/row-gap, 04/39-40). gap ist die Kurzform davon und funktioniert in Flexbox genauso; sonst bräuchte jedes Kind einen eigenen Margin.

(ohne Git, z. B. aus dem ZIP: vorher eine Kopie des Ordners anlegen). Die Lösung steht darunter, erst nachher lesen.

1. Polling-Intervall – Setze POLL_INTERVAL_MS in PokerRoom.tsx:25 auf 20000. Was passiert nach 20 s am Tisch?

Der Server entfernt dich nach 15–20 s, weil der Heartbeat zu selten kommt. Beim nächsten Poll fehlst du in der Liste → «Du bist nicht mehr am Tisch». Zeigt: Polling und Timeout hängen zusammen.

2. Cleanup weglassen – Lösche in HomePage.tsx:72 die Zeile mit window.clearInterval. Geh von der Home-Seite an einen Tisch und schau in den Network-Tab.

Die Liste wird weiter alle 3 s geladen, obwohl die Home-Seite gar nicht mehr zu sehen ist. Das ist das Memory Leak aus 09/30. Mit StrictMode sind es sogar zwei Intervalle.

3. StrictMode-Schutz entfernen – Lösche in PokerTablePage.tsx:43-45 den Block, der den überflüssigen Teilnehmer wieder abmeldet. Tritt einer Session bei.

Im Dev-Modus sitzt du zweimal am Tisch (einmal als Karteileiche, die nach 20 s verschwindet). Zeigt, warum StrictMode Effekte doppelt startet: Der Fehler fällt sofort auf.

4. Session-ID im Header – Zeige in der Kopfzeile in App.tsx:24-26 neben «Scrum Poker» die aktive Session-ID an, aber nur, wenn eine gesetzt ist.

{activeSessionId !== null && <span> · Session {activeSessionId}</span>}. Der State liegt schon in App, also braucht es keine neue Prop. Gutes Beispiel für Conditional Rendering.

5. State direkt ändern – Ersetze in HomePage.tsx:100-102 das filter durch currentSessions.splice(currentSessions.findIndex((s) => s.id === deletedSessionId), 1) und gib danach currentSessions zurück. Lösche eine Session.

Der Eintrag bleibt stehen, bis der nächste Poll kommt. Der Setter bekommt dieselbe Liste (dieselbe Referenz) zurück, darum rendert React nicht neu (08/28, 08/33).

6. Geheimhaltung brechen – Ersetze in store.ts:46 die Bedingung durch true.

Vor dem Aufdecken stehen alle Stimmen in der Antwort (Network-Tab). Die Oberfläche zeigt sie trotzdem verdeckt. Das zeigt: Geheimhaltung muss auf dem Server passieren.

7. Automatisch aufdecken – Lösche in store.ts:166-168 die Prüfung auf eine leere Session. Was passiert, wenn die letzte Person eine Session verlässt und danach jemand neu beitritt?

Ohne Teilnehmer gibt es niemanden ohne Stimme, also wird die leere Session «aufgedeckt». Die nächste Person sieht einen aufgedeckten Tisch ohne Stimmen.

8. Neue Karte – Füge '40' ins Fibonacci-Deck in utils/poker.ts:19 ein (nur im Client). Klicke die Karte an.

Die Karte erscheint, aber der Server antwortet 400 «Diese Karte gibt es im aktuellen Deck nicht.», und die Meldung steht über dem Tisch. Erst wenn '40' auch in rules.ts:9 steht, klappt es. Genau das ist der Preis der doppelten Regeln (B.14).

9. Neuer Deck-Typ – Ergänze in types/poker.ts:4 den DeckType um 'powers' (ohne DECKS anzupassen). Starte im Ordner client/ pnpm build.

TypeScript meldet Fehler überall, wo DECKS[…] steht (z. B. CardDeck.tsx:20 mit DECKS[deck]): Für 'powers' gibt es in DECKS keinen Eintrag. So zeigt TypeScript alle Stellen, die man noch anpassen muss.

10. Statuscode – Ändere in routes/sessions.ts:131 den Code 409 zu 400. Was sieht man im Client, und warum ist 409 passender?

Im Client ändert sich nichts, die Meldung kommt aus { error }. 400 hiesse aber «die Anfrage ist falsch gebaut», dabei ist sie richtig und passt nur nicht zum Zustand der Runde.

11. Fehler simulieren – Stoppe während einer Runde nur den Server (Ctrl+C im Terminal mit server/), der Client läuft weiter.

Meldung «Server nicht erreichbar. Neuer Versuch läuft …», der Tisch bleibt sichtbar (der Vite-Proxy antwortet mit 502). Server neu starten → Daten weg → «Diese Session existiert nicht (mehr)». Erkläre warum.

12. Context ohne Provider – Entferne <UserProvider> und </UserProvider> in main.tsx. Versuche, einen Namen einzugeben.

Das Feld bleibt leer. Ohne Provider gilt der Startwert aus UserContext.ts:12-15: Name '' und ein setName, das nichts tut.

13. Unkontrolliertes <select> – Lösche in DeckSwitcher.tsx:34 die Zeile value={deck}. Wechsle in Fenster B das Deck und schau auf Fenster A.

In A wechseln die Karten, aber die Auswahl zeigt weiter das alte Deck. Ohne value merkt sich der Browser die Auswahl selbst, und sie folgt dem Server-Zustand nicht mehr.

14. Breakpoint – Ändere in HomePage.css:49 768px auf 1200px und verkleinere das Fenster langsam. Wo springt das Layout um? Mit den DevTools (Mobile View, Ctrl+Shift+M) geht das auch.

15. Box-Modell – Entferne die Regel mit box-sizing in index.css:13-17. Wo wird etwas breiter?

Das Namensfeld hat width: 100% plus Padding und Rahmen. Mit content-box wird es breiter als seine Karte und ragt über den Rand.

16. Dritte Ansicht – Baue eine Seite «Hilfe»: eine neue Komponente HelpPage.tsx mit eigener CSS-Datei, ein Button in der Kopfzeile und ein zweiter State in App, der entscheidet, ob die Hilfe zu sehen ist. Erkläre jeden Schritt.

17. Neue API-Route – Baue GET /api/sessions/:sessionId/result, die das Ergebnis einer aufgedeckten Session zurückgibt (sonst 409). Welche Methode, welche Statuscodes, welcher Type in welchen zwei Dateien? Prüfe sie mit curl http://localhost:3000/api/sessions/<id>/result.

18. Lazy Initial Value – Ersetze in useLocalStorage.ts:14-20 die Funktion durch einen direkten Wert. Was ändert sich für den Benutzer, was im Hintergrund?

Für den Benutzer nichts. Aber localStorage.getItem läuft jetzt bei jedem Render, also bei jedem Tastendruck, statt nur einmal (09/8).

19. Datenfluss rückwärts – Starte bei RoundResult.tsx und verfolge, woher participants kommt, bis zum Eintrag im Array sessions im Server.
